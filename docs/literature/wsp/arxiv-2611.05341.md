# Weight-space programming for auditing clinical decision networks

- **Key:** arxiv-2611.05341
- **Authors / organisation:** Humza Nusrat (Henry Ford Health; Michigan State University), Omar Nusrat (Toronto Metropolitan University)
- **Date:** 2026-11-03
- **Link:** https://arxiv.org/abs/2611.05341
- **Kind:** paper
- **Read from:** full text (arXiv HTML v1, including Appendix A with the verbatim instructions). Not read: the companion GitHub repository (https://github.com/hnusrat1/weightspace-rt) with the released answers, black-box testing instructions and per-audit settings, because GitHub access to it was not available in this session; figures were read only through their captions.
- **Relevance to us:** 3 (central)

## What they wanted, and why
Clinical ML models are commissioned by testing on cases with known answers, which cannot expose a shortcut that the test cases share with the training data. The authors ask whether a frontier LLM, given only a written clinical protocol and the raw weights of a small decision network, can (a) say whether the network follows the protocol, (b) describe where it deviates as a logical condition, and (c) repair it by editing weights, with no data, no tools and no code execution. The design is built to separate a real reading of the weights from a guess based on the protocol alone, and a repair from a diagnosis, and to check that a correct network is left alone. The larger goal is weight-level auditing of clinical models before deployment.

## What they studied
Small MLPs (8 inputs, two ReLU hidden layers, one output score; positive = escalate) that screen synthetic head-and-neck radiotherapy planning requests against four protocol rules (A: coverage above hot-spot cap; B: mandible-in-PTV infeasibility, the only two-condition rule; C: cord limit below cord floor; D: missing structure). Main networks: 16 units per layer, 433 parameters; size comparison at 32 and 64 units (1,377 and 4,801 parameters). Flaws were planted through the training data: four confounds (a rule only ever fired together with a partner rule), a 3 Gy shift of the cord threshold ("drift"), and a hidden trigger (a narrow PTV-volume window on missing-structure requests). Three seeds per condition, plus healthy networks. Unit of analysis: individual weights and units of the whole network.

## How they did it
1. Trained a pilot set (rule-B confound) and a panel of 21 networks (7 conditions x 3 seeds); each planted flaw was confirmed by testing before any audit.
2. Each network was given to Claude Opus 5.5 via Claude Code (non-interactive, "high" effort) with all tools disabled, a minimal system instruction copied from the Takehi et al. blog, a fresh session, and the network under a random identifier.
3. The prompt contained the protocol, an input table with ranges, the input scaling, the architecture written as equations, the weight index convention, and every weight to four decimals; the model returned a verdict, deviations as Python boolean conditions on raw inputs, and a list of weight edits in JSON.
4. Audits that hit the output limit twice or ran 45 minutes were resumed once with a request for a final answer ("forced verdicts").
5. Comparisons: the same prompt without weights (three times); two hand-chosen weight statistics (smallest mean first-layer column norm per rule; cord-unit switch-on point from bias/weight); black-box testing (no weights, up to three batches of 50 self-designed queries); exhaustive testing against the protocol written as code; other Claude models; gradient fine-tuning on 200,000 protocol-labelled requests (two schedules, five seeds); a scripted repair told the broken rule; random edits matching the size of the LLM's edits; and writing a network from an all-zero template.
6. Every claim was tested on about 420,000 requests (family test set, a uniform pool, and a dense trigger-window pool) rather than trusted.

## What counts as an explanation here
A verdict plus a list of deviations, each a logical region of input space with the network's and the protocol's decisions, plus a minimal weight patch. The model's free-text account of which units carry which rule was produced but not scored and not checked by ablation. Partial by design: one planted flaw per network.

## How they judged success
Pre-registered scoring rules (fixed before panel answers were read): a claim is verified "strict" if at least 100 requests match and the deviation occurs in at least 80% of them, or "enriched" if it occurs in at least 30% and at least 20x more often than elsewhere. A flawed network is detected if the verdict is "deviates" and verified claims cover at least half its planted-region failures; a healthy network is cleared if the verdict is "follows". Claims were also resampled inside their own region (confirmed / partly right / false). Repairs: planted-region error after edit at or below 5%, count of correct decisions made wrong, number of parameters changed, largest change, and behaviour in 16-bit floating point. Wilson 95% CIs; two sensitivity analyses.

## What they found
- Opus 5.5 named the broken rule in 16 of 18 flawed networks (95% CI 67% to 97%): all 15 confound or drift networks, and 1 of 3 trigger networks.
- Every confound and the drift was visible in single units, and the hand-chosen statistics found the same flaws: column norm found the hidden rule in all 20 confound networks (but none of the drifts or triggers), and the switch-on statistic found all 3 drifts.
- Without weights, the model always ranked rule B most likely but predicted the opposite direction of failure; with weights it named rules A, C and D in all 9 networks carrying those confounds.
- The model's answers show a mix of reading and hand calculation: identifying which inputs a unit uses, computing switch-on points, and hand-evaluating the network at chosen inputs.
- Healthy networks: of 5, 2 cleared without forcing, 1 cleared only by a forced verdict the model called tentative, 1 false alarm (its 2-parameter edit broke 2,018 correct decisions), 1 never reached a verdict.
- Repairs: all 16 detected flaws removed, median 3 parameters changed (range 1 to 53), 14 of 16 broke no correct decision. Edits writing weights of 1e5 or more failed in 16-bit arithmetic, sending every request to "plan".
- Fine-tuning also repaired every network (including triggers, with the network's own schedule) but changed nearly all 433 parameters; gradient training restricted to the units the LLM edited did not reproduce the repair.
- Black-box testing (at most 150 queries, 2-3 minutes) found the four confounds and the drift; testing against the protocol in code separated every flawed network from every healthy one in under a second.
- Sonnet 5.5 matched Opus on the networks given; Haiku 5.5 found confounds but raised a false alarm; Opus 4.6 (half the output budget) reached no verdict on any network; Fable 5.1 first emitted hundreds of calls to a non-existent tool.
- Larger (32/64-unit) rule-B networks were detected and repaired faster than the 16-unit ones, but column norms also found them.
- From the protocol and an all-zero network, the model wrote two networks that decided 100% of 190,778 uniform requests correctly.

## Limits and open problems they name
Tiny networks, synthetic uniform inputs, a four-rule protocol that a few lines of code could implement exactly; all detected flaws were single-unit-visible; distributed flaws not tested; one flaw per network (and the model missed an unplanted missing-structure flaw in all four pilot networks); one model family, one audit per network; no human scoring of explanations; interface effects (monitoring fault, safety-classifier interruptions concentrated on healthy and trigger audits, unknown model version, no reasoning text); formal verification not compared; not preregistered and some statistics defined after flaw types were known; printing weights costs about ten characters per parameter, so the approach cannot reach clinical scale.

## What we take from it
- **A design template (method):** planted-flaw panels with healthy controls, a no-weights prompt control, hand-chosen weight-statistic baselines, black-box query baselines, and claims stated as executable input-space conditions verified on large pools. This is the cleanest known-answer reading protocol in the WSP literature so far.
- **A warning:** reading success on flaws visible in single units can be matched by a trivial statistic; a reading claim needs a baseline of that kind, and the hard cases (certifying a healthy network, distributed or trigger flaws) are where the LLM failed.
- **A measure:** "clear a healthy network" as a separate, harder success criterion than "detect a flaw"; forced verdicts should be scored separately.
- **A shortcut:** asking for deviations as Python boolean conditions makes reading claims machine-checkable.

## K1 detail (reading setup)
- **Reader model(s), and the score for each:** Claude Opus 5.5 (main): 16/18 flawed networks detected; 2/5 healthy cleared unforced. On a 4-network subset: Claude Sonnet 5.5 detected and repaired cap, mandible and drift flaws, healthy verdict "follows" only when forced; Claude Haiku 5.5 detected both confounds, drift repaired but its claimed region covered 26% of failures, false alarm on healthy; Claude Opus 4.6 no verdict on any of 4; Claude Fable 5.1 (2 networks) detected and repaired the mandible confound after an extra message, no verdict on healthy.
- **Target networks:** 8-input MLP, 2 ReLU hidden layers of 16 units (433 parameters), plus 32- and 64-unit variants (1,377 and 4,801 parameters), single scalar output; trained (AdamW) to decide escalate vs. plan for synthetic radiotherapy planning requests, with one planted flaw each (confound, threshold drift, or trigger) or none.
- **How the weights were presented:** as text inside the single prompt; decimal numbers rounded to four decimal places (the same rounded weights were used for all evaluations); laid out as named matrices W1 (16 rows x 8 columns), b1, W2 (16 x 16), b2, w3 (1 x 16), b3, with each row labelled by unit and the column order of input names given in a comment. Total tokens: not stated (the paper says about ten characters per parameter).
- **Prompt:** (1) purpose of the network and meaning of the output score; (2) the protocol as four rules with formulas; (3) an input table with names, meanings and ranges; (4) input scaling (center and scale vectors); (5) the architecture as equations with the index convention; (6) the weights; (7) task: working from the weights alone, decide whether the network follows the protocol everywhere in range (ignoring disagreements within 0.3 Gy/cc of a threshold), describe each deviation, and edit the weights minimally while keeping architecture and scaling; make no edits if it follows; (8) a required JSON format (verdict, deviations with Python condition and both decisions, edits). No candidate answer list. System prompt "Answer the user's request." The verbatim prompt is in the paper's Appendix A; the release (all instructions, answers and settings) is stated to be at https://github.com/hnusrat1/weightspace-rt (not read here).
- **Access regime:** no tools at all (no file access, no code execution, no data); output limit per reply about 128,000 tokens for Opus/Sonnet/Haiku 5.5 and about 64,000 for Opus 4.6 and Fable 5.1, with an automatic "continue" after the first limit hit; stopped after the second hit or 45 minutes, then one message requesting a final answer. A first set of seven audits at "max" effort produced no answer in 66 minutes (about 480,000 output tokens each). Black-box comparison: no weights, up to three batches of 50 queries.
- **Controls:** no-weights prompt (3 repeats); healthy networks; column-norm and switch-on weight statistics with no LLM; black-box query testing; random edits of matched number and size; scripted repair; fine-tuning; exhaustive testing against protocol code; claims resampled in their own regions.
- **Failure modes observed:** running out of budget without a verdict (especially on healthy networks and for Opus 4.6); forced verdicts falling back to a default "follows" or to the protocol's most salient rule (rule B), producing false alarms; missing an unplanted flaw; trigger detection 1/3; claimed region too narrow (Haiku on drift); repairs with huge weights that overflow in fp16; Fable 5.1 hallucinating tool calls; safety-classifier interruptions concentrated on healthy and trigger audits.
- **Prompt or format choices that helped or hurt:** the authors do not run a prompt ablation. Stated observations: "max" effort without a time limit produced no answers within 66 minutes; the longer repeated audits (up to about 300,000 tokens) cleared a healthy network that first-round budgets could not; a smaller per-reply budget coincided with no verdicts (confounded with model generation); requiring deviations as executable conditions enabled verification. No other format comparisons.
