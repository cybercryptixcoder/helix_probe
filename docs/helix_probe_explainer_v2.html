0. In one page

The problem. Point a loop at a black box and have it learn how the box works by trial and error, in small steps a cheap model can do reliably, with nothing in the core tied to any particular box.

The three problems it has to solve (from the Helix Evolve days): continuity (every trial builds on the last), bounded context (each call sees what it needs, not everything), and narrow jobs (each call does one thing well). v1's live runs added a fourth: the model must follow the evidence, not defend itself by piling up exceptions (v1's grid run) or by trusting its own unchecked words (v1's knob run).

v2's answer, in four ideas:

  1. The box is the evaluator, and models are judged on evidence they never saw. A few random probes are run at the start and sealed (the exam). A model only replaces the current one if it predicts the exam at least as well. Memorising the notebook can't raise that score.
  2. Three roles in series. The experimenter chooses one probe; the updater revises the model on a surprise; the theorist writes a model from scratch from the evidence alone, without seeing the current model, so it can't inherit its patches.
  3. One model artifact. The beliefs are comments inside predict(); the words and the code can't disagree.
  4. Signals that work on any box. Exam score, on-arrival hits, fit, model size. Nothing in the core knows what a probe contains.

3. The evaluator: is one needed, and what it is here

In Helix Evolve the evaluator scored the artifact (a program) against an objective, and that score was the sense of progress. Here the artifact is the model, and the only judge of a model is the box. Every probe is a test the current model takes before it sees the answer.

v1 scored models on the notebook. That score can be gamed: a lookup table of past probes scores 100%. v2 scores them first on the exam: a few random probes run at the start whose results no LLM call ever sees. A rule that captures the mechanism predicts them; a memorised case can't. That is the whole answer to "a real model vs a list of exceptions": not "fewer rules", but "rules that predict what they weren't fitted to". A real exception (a wall, a corrupted interval) passes, because it predicts every future probe that touches it.

The roles see their scores, so they have a sense of progress, but they can't see the exam's contents, so they can't fit it.

Where it is wrong: older experiments it mispredicts (max 8)
The latest 5 experiments in full
An index line for each older experiment (max 80)
The job: PROPOSE, or REVISE with the surprise
Theorist
The box: brief, probe format, library
The evidence: every experiment, probe → observation (the latest 150)
The job: THEORIZE, with the same modelling rules

Nothing about any model, any score, or which experiments were surprising: those would all carry the current model's view.

7. How v1 and v2 are compared

The benchmark: FIND (MIT/Northeastern, NeurIPS 2023). The agent probes a black-box function and writes code that reproduces it. FIND's official scorers:

  • numeric (40 functions in our sample: 10 small neural networks, 30 written formulas, many with an interval where they behave differently): solved if the normalised squared error on x = −127.5 ... 127.5 is under 0.1. Ceiling on our sample: 36/40, because 4 functions return fresh random noise in their odd interval, so even the true function can't match a second draw.
  • strings (40 functions, most of them compositions of two string operations): share of FIND's 10 test pairs per function reproduced exactly.

The arms, each on the same functions, each function a fresh run with its own memory:

ArmWhat it isolates
v2the system
v2-randomv2 with experiments drawn at random: does choosing experiments matter? (your core claim: directed reasoning beats sampling)
v2-no-theoristwhat the theorist adds
v1the frozen first version (same transport; its mechanism unchanged)
published: GPT-4, GPT-3.5, Llama-2-70B, -13BFIND's own agents, their released answers scored by the same scorer on the same functions

Budget is reported two ways, because FIND's GPT-4 agent used only about 3 experiment rounds (about 20 inputs) per function: the score each run had after 3 experiments, and its final score. Inputs used, model calls and cost are reported per arm.

Dev vs test. Design choices were tried on a separate 16-function dev set (bench/find/dev), never on the 80 reported functions.
