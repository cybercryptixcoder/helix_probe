0. The whole system on one board

Helix Probe learns how a black box works by running one small experiment at a time. What it learns is a model: a Python function predict(probe) that says what the box will do. The model has to predict every experiment before the box answers. That one requirement is the whole idea: a model that only explains the past can fake it, but a model that keeps predicting the future can't. Click any box below.

Click a box.

Each step is one trip around this board. Three of the boxes are model calls, each with its own short system prompt and one call at a time, in series: the experimenter, the updater and the theorist. Everything else is code: running the model, scoring, deciding what is kept, planning. The box is the ground truth. When a model and the box disagree, the model changes. The box is never "explained away" with an exception list.

1. Two rules decide everything

Fixes must explain the past. An updater's edit replaces the current model only if it fits the notebook better (average match over every experiment so far). On a tie, the shorter model wins.
New theories must predict the future. A theorist's model is not judged on the notebook at all, because a fresh model can always be written to fit what it was shown. It goes on trial: for the next 3 experiments, both it and the current model predict each one before the box answers. It takes over only if it predicted them at least as well. On a tie, fit decides, then size.

Why two rules and not one:

  • Repairs are small and local: "the model got E12 wrong; change it so E12 comes out right and nothing else breaks". Fit on the past is the right test for that. Shorter-wins keeps the repairs from piling up into a lookup table.
  • Theories are big jumps, and the danger is the opposite one: a theory written to fit 30 experiments can memorise them. So a theory has to earn its place on experiments that did not exist when it was written. That is the same test as the sealed exam in v2, but it costs nothing extra: the experiments would have been run anyway.

v2 judged everything by a sealed exam of 4 random probes that no model call ever saw. It worked on FIND, but:

  • the exam costs 4 probes per run;
  • it can't exist for a game, because a random probe on a game changes the game;
  • at the start, a wrong model and an empty one both score 0 on it.

v3 keeps it as an option (--exam 4, the v3-exam arm) so the two can be compared on FIND.

2. Boxes that remember (hidden state)

Some boxes keep state you can't see:

  • a lock that counts presses;
  • a game whose screen doesn't show everything;
  • a service with a cache.

A model that sees only the current screen cannot be right about these, however clever it is: the same screen and the same action lead to different results.

It isn't rare. Random play on 8 ARC-AGI-3 games showed that in 3 of them, the same screen plus the same action sometimes led to different next screens:

  • g50t: 287 of 1,200 transitions;
  • cd82: 67;
  • wa30: 69.

v3's answer is general, not ARC-specific. A box declares stateful = True, and then:

  1. every probe the model sees carries the history, meaning every action since the last reset, plus what the box shows now;
  2. the prompts tell the roles to keep hidden state explicitly, by replaying the history inside predict() ("count the presses since the reset", "track where the cursor is");
  3. the box is restored after a crash by replaying the recorded actions, so the hidden state comes back too.

The test box for this is envs/hidden_lock.py:

  • pressing A raises a hidden counter;
  • a lamp shows only whether the counter is at least 2;
  • B opens the door only when the counter is exactly 3.

In the offline test, a model that only looks at the lamp fits 0.99, and a model that counts from the history fits 1.00. The trial rule picks the one that counts (tests/test_v3.py). Section 4 shows a live run on it.

3. Using the model: planning through it

A model is worth having if you can use it. If the box has a goal (a level to complete, a door to open), each step begins with a question to code: can the current model reach the goal?

  • Code searches breadth-first through the model: from where the box is now, it tries each action, asks the model what happens, moves to the predicted state, and repeats. It never touches the real box while searching.
  • If the model says some sequence of actions reaches the goal, the first piece of that sequence (up to the box's max_probe actions) is run for real, as an experiment like any other. The model predicted it, so a surprise is a lesson.
  • If not, the experimenter chooses an experiment.

There is no separate "solver" and no search over models: the plan is only as good as the model, which is the point. When the plan fails, the box has shown exactly where the model is wrong.

The experimenter itself is told the goal and asked for experiments that teach the most about reaching it. Every second experiment is a random ordinary probe from the box. On the knob box, choosing every experiment ended at 51% and 45% held-out (two seeds), against 100% for mixed: a chooser alone keeps asking where it already looks.

A budget in the box's own units (actions in ARC, inputs in FIND) stops the run when spent.

The pieces are deliberately few. The core is probe/loop.py (the board), probe/prompts.py (the three roles), probe/memory.py (notebook, model), probe/simulate.py (runs a model in a sandbox), probe/llm.py (the model client) and probe/env.py (the adapter interface). There is no population, no optimizer and no scheduler.

7. Never lose a run

  • Everything is written as it happens, append-only, with the current trial saved atomically. A kill mid-step loses at most that step. A torn last line is dropped on reading.
  • Resume is the same command with the same folder: finished runs are skipped, and unfinished ones continue from their notebook, model and trial. Stateful boxes are restored by replaying their actions.
  • Graceful stop: on a stop signal every run finishes its step, saves, and the job pushes and exits.
  • From GitHub alone: the VM job pushes every run folder to results/ every 30 minutes, with traces gzipped. bench/restore.py rebuilds the run folders from there, so a fresh clone continues where the last push left it. Give it a bigger --steps and it goes further, for example from experiment 80 to 120.
  • Tested: a stateful run with a theory mid-trial was published, deleted, restored and continued from 6 to 10 experiments with the trial intact; the whole job was run from a fresh clone with a fake model; stop and resume with kill -TERM; the job waiting on another job's lock.

9. The runs: every run is an experiment and an attempt

Every run is set up to do two things:

  • tell us something about the next change;
  • attempt a result that can stand next to a published one. That means copying the published setup as closely as possible, then beating it fairly: with a weaker model and tighter limits.
